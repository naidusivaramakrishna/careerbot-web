  1. GENERAL CONVENTIONS
================================================================================

  Base URL:        https://api.careerbot.in/api/v1
  Content-Type:    application/json
  Date format:     ISO 8601  (e.g.  2026-01-15T10:30:00.000Z)
  Currency:        INR (Indian Rupee)
  Auth header:     Authorization: Bearer <access_token>

  All successful responses use HTTP 200 (or 201 for creation).
  All error responses follow the unified error schema in Section 13.

  Pagination default: page=1, limit=20


================================================================================
  2. AUTHENTICATION
================================================================================

  All endpoints listed in this document require a valid JWT Bearer token.
  The token is obtained via the existing Auth APIs (login / Google OAuth).

  Token expiry: 24 hours (access), 30 days (refresh)
  Refresh endpoint: POST /api/v1/auth/refresh   (existing, not documented here)

  If the token is expired or invalid, all endpoints return:
    HTTP 401  { "error": "UNAUTHORIZED", "message": "Token expired or invalid" }

  Response Body (HTTP 200):
  {
    "plan_id":           "string  — current plan ID",
    "plan_name":         "string  — current plan name",
    "status":            "string  — 'active' | 'cancelled' | 'expired' | 'trial'",
    "billing_cycle":     "string? — 'monthly' | 'yearly' (null for FREE)",
    "started_at":        "string  — ISO date subscription started",
    "expires_at":        "string? — ISO date; null for FREE plan",

    "credits_total":     "number  — credits allocated in current billing period",

    "credits_remaining": "number  — credits still available",
    "next_reset_at":     "string? — ISO date of next credit reset (null for FREE)"
  }

  Subscription status rules:
    'active'    — plan is active and within expiry date
    'cancelled' — user cancelled; still active until expires_at
    'expired'   — plan past expires_at; downgrade to FREE behavior
    'trial'     — user is on a trial period (if offered)

  ────────────────────────────────────────────────────────────────────────────
  POST  /api/v1/subscription/upgrade
  ────────────────────────────────────────────────────────────────────────────

  Description:
    Initiates an upgrade to a paid plan. Returns a Razorpay checkout URL.
    The frontend redirects the user to complete payment on Razorpay.

  Request Body:
  {
    "plan_id":       "string  — 'PRO' | 'MAX'",
    "billing_cycle": "string? — 'monthly' (default) | 'yearly'"
  }

  Response Body (HTTP 200):
  {
    "success":      true,
    "checkout_url": "string  — Razorpay checkout URL",
    "order_id":     "string  — Razorpay order ID (for post-payment verification)"
  }

  Errors:
    400 — Invalid plan_id or already on this plan
    402 — Payment initiation failed on Razorpay

  ────────────────────────────────────────────────────────────────────────────
  POST  /api/v1/subscription/cancel
  ────────────────────────────────────────────────────────────────────────────

  Description:
    Cancels the user's subscription at end of current billing period.
    Access and credits remain until expires_at.

  Request Body:
  {
    "reason": "string? — cancellation reason (optional, for internal analytics)"
  }

  Response Body (HTTP 200):
  {
    "success":    true,
    "expires_at": "string  — ISO date when plan access ends",
    "message":    "string  — user-facing confirmation message"
  }

  ────────────────────────────────────────────────────────────────────────────
  POST  /api/v1/subscription/webhook   (Razorpay Webhook)
  ────────────────────────────────────────────────────────────────────────────

  Description:
    Receives Razorpay payment events. Backend MUST verify HMAC-SHA256
    signature before processing. Used to activate upgrades after payment.

  Headers:
    X-Razorpay-Signature: <hmac_sha256_signature>

  Request Body: Standard Razorpay webhook payload

  Supported events:
    payment.captured  — Payment succeeded → activate plan + credit account
    payment.failed    — Payment failed → send notification to user
    subscription.cancelled — Razorpay-initiated cancel

  Response: HTTP 200  { "status": "ok" }

  Behaviour on payment.captured:
    1. Verify signature; reject (HTTP 400) if invalid
    2. Look up order_id → user
    3. Update user plan: plan_id, credits_total, credits_remaining, expires_at
    4. Set started_at, auto_renew = true
    5. Create notification (type: 'credit', title: 'Plan Activated')
    6. Return { "status": "ok" }

  Notes:
    • Idempotent — processing the same order_id twice must not double-credit
    • Log all webhook payloads for audit trail

  ────────────────────────────────────────────────────────────────────────────
  POST  /api/v1/credits/deduct
  ────────────────────────────────────────────────────────────────────────────

  Description:
    Internal service-to-service endpoint. Called by backend feature services
    after a billable AI action completes successfully.
    NOT accessible by the user's frontend JWT — requires service account auth.

  Request Body:
  {
    "user_id":     "string  — user UUID",
    "feature":     "string  — feature key from CREDIT_COSTS table (Section 10)",
    "tokens_used": "number  — LLM tokens consumed",
    "cost_inr":    "number  — actual INR cost to platform",
    "from_cache":  "boolean — was result served from cache?",
    "details":     "object? — feature-specific metadata for usage log"
  }

  Response Body (HTTP 200):
  {
    "success":           true,
    "credits_deducted":  "number — credits that were deducted",
    "credits_remaining": "number — user balance after deduction",
    "log_id":            "string — ID of the created usage log entry"
  }

  Deduction rules:
    • Credits are deducted AFTER a successful AI operation, never before.
    • If AI operation fails, do NOT call this endpoint.
    • Cached results (from_cache: true) still deduct credits — cache is
      transparent to the user. Platform just had $0 AI cost.

  Errors:
    402 — Insufficient credits:
          {
            "error":             "INSUFFICIENT_CREDITS",
            "credits_required":  10,
            "credits_remaining": 3
          }
    400 — Unknown feature key

================================================================================
  8. PROFILE COMPLETENESS LOGIC  (Backend Computation)
================================================================================

  The profile.completeness field in the dashboard summary is computed by the
  backend only — the frontend displays it, never calculates it.

  Field weighting:

  Field                      | Weight
  ───────────────────────────|────────
  Full Name                  |  10%
  Email (verified)           |   5%
  Phone number               |   5%
  Location (city / country)  |   5%
  Profile picture uploaded   |   5%
  LinkedIn URL               |   5%
  Professional summary       |  10%
  Skills (>= 3 skills added) |  15%
  Work experience (>= 1 job) |  15%
  Education (>= 1 degree)    |  10%
  Projects (>= 1 project)    |   5%
  Certifications (>= 1)      |   5%
  ───────────────────────────|────────
  TOTAL                      | 100%

  Computation rules:
    • completeness is an integer 0–100
    • profile_completed (in progress flags) = true when completeness >= 60
    • missing_fields array must contain human-readable names of incomplete
      fields only (e.g. "LinkedIn URL", "Skills", "Work Experience")
    • Empty string values count as missing.
    • Whitespace-only string values count as missing.
    • Skills threshold: fewer than 3 skills = field counts as missing.

  Example when completeness = 75:
    missing_fields: ["LinkedIn URL", "Certifications", "Projects"]


================================================================================
  9. RECOMMENDED STEP PRIORITY LOGIC  (Backend Computation)
================================================================================

  Backend evaluates progress flags in this order and returns the first
  incomplete step. Steps are numbered 1–5. Step 0 = special upgrade prompt.

  Priority order:

  Priority | Condition check                        | step_number | step_name
  ─────────|────────────────────────────────────────|─────────────|──────────────────
  0 (HIGH) | credits_remaining < 6                  | 0           | "Upgrade Plan"
           | (less than 2x lowest credit cost of 5) |             |
  1        | resume_uploaded == false               | 1           | "Upload Resume"
  2        | profile_completed == false             | 2           | "Complete Profile"
  3        | ats_scan_done == false                 | 3           | "ATS Scan"
  4        | resume_enhanced == false               | 4           | "Enhance Resume"
  5        | job_applied == false                   | 5           | "Browse & Apply"
  5 (DONE) | all steps complete                     | 5           | "Browse & Apply"

  Standard step objects to return:

  Step 1 — Upload Resume:
    title:          "Upload & Parse Your Resume"
    description:    "Upload your resume to auto-fill your profile and save time."
    credit_cost:    5
    estimated_time: "~15 seconds"
    cta_text:       "Upload Resume"
    cta_path:       "/parser"
    icon:           "Upload"

  Step 2 — Complete Profile:
    title:          "Complete Your Profile"
    description:    "A complete profile improves your job matches by up to 40%."
    credit_cost:    0
    estimated_time: "~5 minutes"
    cta_text:       "Complete Profile"
    cta_path:       "/profile"
    icon:           "User"

  Step 3 — ATS Scan:
    title:          "Check Your ATS Score"
    description:    "Find out how well your resume matches ATS systems and get optimization suggestions."
    credit_cost:    5
    estimated_time: "~15 seconds"
    cta_text:       "Start ATS Scan"
    cta_path:       "/ats"
    icon:           "Search"

  Step 4 — Enhance Resume:
    title:          "Enhance Your Resume with AI"
    description:    "Let AI rewrite and optimize your resume for maximum impact."

  11. CREDIT CONFIRMATION MODAL LOGIC  (Frontend Reference for Backend)
================================================================================

  Before running a credit-costing feature, the frontend calls
  POST /api/v1/credits/check and then applies this logic to decide
  whether to show a confirmation dialog:

  Show modal IF any of:
    1. First time user is using any credit-costing feature (localStorage check)
    2. Action costs >= 10 credits
    3. credits_remaining < (credit_cost * 2)  — low balance warning
    4. Action costs 5–9 credits AND user preference != 'high_cost_only'

  Skip modal IF:
    Action costs < 5 credits (show inline note only)

  This logic is frontend-only. The backend enforces actual credit availability
  at deduction time via the /credits/deduct endpoint.

  13. ERROR RESPONSE FORMAT
================================================================================

  All API errors return a consistent JSON body:

  {
    "error":   "string  — machine-readable error code (SCREAMING_SNAKE_CASE)",
    "message": "string  — human-readable message (safe to display to user)",
    "details": "object? — additional context (validation errors, field names, etc.)"
  }

  Standard error codes:

  HTTP | Error Code                 | When
  ─────|────────────────────────────|────────────────────────────────────────────
  400  | INVALID_REQUEST            | Malformed request body or params
  400  | UNKNOWN_FEATURE            | Unknown feature key in credit operations
  401  | UNAUTHORIZED               | Missing, expired, or invalid JWT token
  402  | INSUFFICIENT_CREDITS       | Not enough credits for the requested action
  403  | FORBIDDEN                  | Valid token but no permission for resource
  404  | NOT_FOUND                  | Resource not found (notification, invoice)
  409  | ALREADY_ON_PLAN            | User trying to upgrade to current plan
  422  | VALIDATION_ERROR           | Field-level validation failure
  429  | RATE_LIMIT_EXCEEDED        | Too many requests from this user
  500  | INTERNAL_ERROR             | Unexpected server error (log, don't expose)

  INSUFFICIENT_CREDITS — extended fields:
  {
    "error":             "INSUFFICIENT_CREDITS",
    "message":           "Not enough credits to run this feature.",
    "credits_required":  10,
    "credits_remaining": 3,
    "upgrade_url":       "/pricing"
  }

  VALIDATION_ERROR — extended fields:
  {
    "error":   "VALIDATION_ERROR",
    "message": "Validation failed.",
    "details": {
      "fields": [
        { "field": "plan_id", "message": "Invalid plan ID." }
      ]
    }
  }

  14. RATE LIMITING & SECURITY NOTES
================================================================================

  Recommended rate limits (per authenticated user, per minute):

  Endpoint                                 | Limit
  ─────────────────────────────────────────|────────
  GET  /api/v1/dashboard/summary           | 60/min
  GET  /api/v1/credits/balance             | 120/min  (cached 30s)
  GET  /api/v1/notifications/count         | 60/min   (poll endpoint)
  GET  /api/v1/notifications               | 60/min
  POST /api/v1/credits/check               | 60/min
  POST /api/v1/credits/deduct              | 30/min   (service account only)
  POST /api/v1/subscription/upgrade        | 5/min
  POST /api/v1/subscription/cancel         | 5/min
  PATCH /api/v1/notifications/:id/read     | 120/min
  POST  /api/v1/notifications/read-all     | 20/min

  Security requirements:
    1. POST /api/v1/credits/deduct is BACKEND-to-BACKEND only.
       Must require a service account token, NOT the user's JWT.
       Never expose this endpoint to the browser/frontend directly.

    2. POST /api/v1/subscription/webhook must verify HMAC-SHA256 signature
       from Razorpay before any processing. Reject unverified requests with
       HTTP 400. Never trust webhook payload without signature check.

    3. Invoice PDF download URLs must be pre-signed with a 15-minute TTL.
       Do not expose permanent S3 URLs.

    4. Never expose tokens_used or cost_inr fields in user-facing API
       responses. These are strictly internal / admin-only metrics.

    5. All responses must include security headers:
         Content-Security-Policy
         X-Content-Type-Options: nosniff
         X-Frame-Options: DENY

    6. credits_remaining must never go negative. If a race condition would
       cause credits to go below 0, reject the deduction with 402.

  |                  |MongoDB |    | Redis  |    | Azure  | <----+           |
  |                  |        |    | Cache  |    | OpenAI |                  |
  |                  +--------+    +--------+    +--------+                  |
  |                                                                          |
  +--------------------------------------------------------------------------+

  CRITICAL RULE: Frontend NEVER calls AI Layer directly.
                 All AI calls go through Backend.

  LAYER RESPONSIBILITIES FOR DASHBOARD:

  FRONTEND:
    - Render dashboard UI (components, layouts, navigation)
    - Display credit balance from X-Quota-Remaining headers
    - Show confirm modal before credit-consuming actions
    - Handle 402 responses (show upgrade modal)
    - Sync credit balance across tabs (BroadcastChannel API)
    - Display loading skeletons and error states

  BACKEND:
    - Compute recommended_step and profile_completeness (NOT frontend)
    - Enforce quota (atomic Lua script: check + deduct)
    - Refund credits on AI call failure (INCRBY on 5xx)
    - Cache dashboard summary (Redis, 5 min TTL)
    - Invalidate cache after credit-consuming actions
    - Log usage from AI Layer responses (backend captures tokens_used)
    - Return X-Quota-Remaining header in every response
    - Compute onboarding state and persist steps

  AI LAYER:
    - Process AI requests (parse, enhance, score, match)
    - Return tokens_used, cost_inr, from_cache in every response
    - NO changes needed for dashboard (zero modifications)

 2. DATA FLOW DIAGRAMS (6 Flows)
================================================================================

FLOW 1: CREDIT-CONSUMING ACTION (e.g., ATS Scan)
-------------------------------------------------
  User clicks "Scan" (5 credits)
    |
    v
  [Frontend] CreditConfirmModal (adaptive: show if first-use or >= 10 credits)
    |  User confirms
    v
  [Frontend] POST /ats/score  (with httpOnly cookie)
    |
    v
  [Backend] Auth Middleware --> extract user_id from cookie
    |
    v
  [Backend] QuotaEnforcement Middleware
    |  Redis Lua Script (ATOMIC):
    |    1. Check feature limit (ats_scan < plan.ats_limit)
    |    2. Check credit balance (balance >= 5)
    |    3. Deduct credits (DECRBY 5)
    |    4. Increment feature count (INCR ats_scan)
    |  Returns: { allowed: true, remaining: 40 }
    |
    |  If insufficient: Return 402 + { error: "quota_exhausted", ... }
    v
  [Backend] ATS Endpoint --> calls AI Layer POST /api/v1/scoring/ats
    |
    v
  [AI Layer] Processes resume --> returns score + tokens_used
    |
    v
  [Backend] On SUCCESS:
    |  1. Log to usage_logs collection (feature, credits, tokens, cost)
    |  2. Log to activity in user record
    |  3. DELETE Redis key dashboard:{user_id} (CACHE INVALIDATION)
    |  4. Set header X-Quota-Remaining: 40
    |  5. Return AI response + credit info to frontend
    |
    |  On AI FAILURE (5xx):
    |  1. INCRBY quota:{user_id}:balance 5 (REFUND)
    |  2. DECR quota:{user_id}:feature:ats_scan (UNDO count)
    |  3. Return 502 with error to frontend
    v
  [Frontend] On SUCCESS:
    |  1. Update credit state from X-Quota-Remaining header
    |  2. Broadcast new balance via BroadcastChannel
    |  3. Show result + "5 credits used, 40 remaining"
    |
    |  On 402 (quota exhausted):
    |  Show InsufficientCreditsModal --> link to /pricing
    |
    |  On 5xx (AI failure):
    |  Show error toast: "Something went wrong. Credits not deducted."


FLOW 2: DASHBOARD LOAD (Every Login)
-------------------------------------
  User navigates to /dashboard
    |
    v
  [Frontend] GET /users/me/dashboard-summary (with cookie)
    |
    v
  [Backend] Check Redis: dashboard:{user_id}
    |
    |  CACHE HIT (< 5 min old):
    |    Return cached summary + header X-Quota-Remaining
    |
    |  CACHE MISS:
    |    Aggregate from MongoDB:
    |      - users (plan, credits, onboarding)
    |      - user_profiles (completeness fields)
    |      - resumes (count, best score)
    |      - match_results (best match)
    |      - assessment_sessions (interview score)
    |      - usage_logs (recent activity, usage by feature)
    |    Compute: profile_completeness (weighted formula)
    |    Compute: recommended_step (state machine)
    |    Store in Redis: dashboard:{user_id} (TTL: 5 min)
    |    Return summary
    v
  [Frontend] Render dashboard:
    - WelcomeBanner (name, plan)
    - PlanStatusCard (plan name, credits remaining/total)
    - CreditBalanceCard (progress bar)
    - ProfileCompletenessCard (% from backend)
    - RecommendedNextStep (from backend recommended_step)
    - ProgressStepper (completed_steps from backend)
    - QuickActionGrid (8 cards with costs)
    - RecentActivity (from dashboard-summary.recent_activity)
    - ScoreSummary (best ATS, match, interview scores)


FLOW 3: ONBOARDING (First-Time User)
--------------------------------------
  User registers (POST /auth/register)
    |
    v
  [Backend] Create user:
    - role: USER
    - plan_id: FREE
    - credits_remaining: 50
    - onboarding_step: 0  (not started)
    - onboarding_completed: false
    |
    v
  [Frontend] Redirect to /onboarding
    |
    v
  Screen 1/3: Personal Info (name, phone, location, career_stage)
    |  User fills form, clicks "Continue"
    v
  [Frontend] PUT /profile/update (save immediately)
  [Frontend] POST /users/me/onboarding-progress { step: 1 }
    |
    v
  [Backend] Save profile fields + set onboarding_step: 1 in user record
    |
    v
  Screen 2/3: Resume Upload (optional)
    |  User uploads PDF (or clicks "Skip")
    v
  IF UPLOADED:
    [Frontend] POST /parser/parse_resume
    [Backend] Deduct 5 credits --> call AI Layer --> return parsed data
    [Frontend] PUT /profile/import/resume (auto-fill profile)
    [Frontend] POST /users/me/onboarding-progress { step: 2 }

  IF SKIPPED:
    [Frontend] POST /users/me/onboarding-progress { step: 2 }
    |
    v
  Screen 3/3: Welcome Summary
    |  User clicks "Go to Dashboard"
    v
  [Frontend] POST /users/me/onboarding-complete
  [Backend] Set onboarding_completed: true, onboarding_step: 3
  [Frontend] Navigate to /dashboard

  ABANDONMENT RECOVERY:
    Next login: Backend returns onboarding_step in user profile.
    If onboarding_step < 3 AND onboarding_completed == false:
      Frontend redirects to /onboarding?step={onboarding_step}
      Wizard resumes from saved step (previous data already persisted).


FLOW 4: CACHE INVALIDATION (After Any Credit-Consuming Action)
---------------------------------------------------------------
  After ATS scan / enhance / parse / match / assessment:
    |
    v
  [Backend] DELETE Redis key: dashboard:{user_id}
  [Backend] DELETE Redis key: quota:{user_id}:summary (if exists)
    |
    v
  Next dashboard load: CACHE MISS --> fresh aggregation from MongoDB


FLOW 5: CROSS-TAB CREDIT SYNC
-------------------------------
  Tab A: User does ATS scan (5 credits deducted)
    |
    v
  [Frontend Tab A] Receives X-Quota-Remaining: 40
    |
    v
  [Frontend Tab A] BroadcastChannel.postMessage({ type: 'CREDIT_UPDATE', remaining: 40 })
    |
    v
  [Frontend Tab B] BroadcastChannel.onmessage --> updates DashboardContext.credits = 40
    |
    v
  Tab B shows updated balance without page refresh.

  FALLBACK (BroadcastChannel not supported):
    On window focus event: GET /users/me/quota (lightweight endpoint, no cache)


FLOW 6: PLAN UPGRADE
---------------------
  User clicks "Upgrade" on pricing page
    |
    v
  [Frontend] POST /subscription/upgrade { plan_id: "BASIC" }
    |
    v
  [Backend] Create Razorpay checkout session
    |  Return: { checkout_url, order_id }
    v
  [Frontend] Redirect to Razorpay payment page
    |  User completes payment
    v
  [Razorpay] POST /subscription/webhook { order_id, payment_status }
    |
    v
  [Backend] On payment_success:
    1. Update user.plan_id = "BASIC"
    2. SET Redis quota:{user_id}:balance = 200 (new plan credits)
    3. SET Redis quota:{user_id}:plan = "BASIC"
    4. DELETE Redis dashboard:{user_id} (invalidate cache)
    5. Log to billing_history collection
    6. Send confirmation email
    |
    v
  [Frontend] Redirect to /dashboard (shows new plan + credits)

 4. FIRST-TIME USER JOURNEY (Onboarding with Step Persistence)
================================================================================

DESIGN PRINCIPLE: Every onboarding step saves data IMMEDIATELY.
If user closes browser at Step 2, they resume at Step 2 on next login.
No data is lost. No wizard restart.

+-----------------------------------------------------------------------------+
|                     FIRST-TIME USER FLOW (7 STEPS)                          |
|                                                                             |

|  +------------------------------------------+                               |

|  |      role: USER                           |                               |
|  |      plan_id: FREE                        |                               |
|  |      credits_remaining: 50                |                               |
|  |      onboarding_step: 0                   |                               |
|  |      onboarding_completed: false          |                               |
|  |  --> Sets httpOnly cookie                 |                               |
|  |  --> Redirect to /onboarding              |                               |
|  +------------------------------------------+                               |
|                      |                                                      |
|                      v                                                      |
|  STEP 2: ONBOARDING WIZARD (3 screens, ~60 seconds)                        |
|                                                                             |
|  Screen 1/3: "Tell us about yourself"                                       |
|  +------------------------------------------+                               |
|  |  Full Name:     [________________]        |                               |

|  +------------------------------------------+                               |
|  |  [check] Account created                  |                               |

|  |  [check] Profile 35% complete             |  (or 65% if parsed)          |
|  |                                           |                               |
|  |  Here's what you can do:                  |                               |
|  |  [Build Resume] [ATS Scan]                |                               |
|  |  [Enhance]      [Find Jobs]               |                               |
|  |                                           |                               |
|  |        [Go to Dashboard -->]              |                               |
|  +------------------------------------------+                               |
|  On "Go to Dashboard":                                                      |
|    --> POST /users/me/onboarding-complete                                   |
|    --> Backend: onboarding_completed = true, onboarding_step = 3            |
|    --> Navigate to /dashboard                                               |
|                                                                             |
|  STEP 3-7: (Same as V2 -- Dashboard, Explore, Credits Low, Upgrade)        |
+-----------------------------------------------------------------------------+

ONBOARDING STATE SOURCE-OF-TRUTH:
  MongoDB user document (onboarding_step, onboarding_completed) is the
  SINGLE SOURCE OF TRUTH. Redis key onboarding:{user_id} is an optional
  read-through accelerator only.
    - On POST /onboarding-progress: write to BOTH MongoDB + Redis
    - On read: check Redis first; if missing/expired, read from MongoDB
    - If Redis is down: onboarding still works (reads from MongoDB)
    - Redis TTL = 24 hours; user record has no TTL (permanent)

ABANDONMENT RECOVERY LOGIC:
  On every login (in middleware.ts or layout.tsx):
    1. Fetch user profile (already happens for auth)
    2. Check: onboarding_completed == false?
    3. If false: redirect to /onboarding?step={onboarding_step}
    4. Wizard reads step from URL param and resumes from that screen
    5. Previous steps' data already saved (name, phone, etc.)
    6. User sees their data pre-filled, continues from where they left off

  EDGE CASES:
    - User registered via OAuth but never visited onboarding:
      onboarding_step=0, redirect to Step 1
    - User filled Step 1, closed browser:
      onboarding_step=1, redirect to Step 2 (name/phone pre-filled)
    - User uploaded resume in Step 2, closed before Step 3:
      onboarding_step=2, redirect to Step 3 (resume already parsed)

================================================================================
 8. CACHE STRATEGY & INVALIDATION RULES
================================================================================

REDIS CACHE FOR DASHBOARD:

  KEY: dashboard:{user_id}
  TYPE: STRING (JSON-serialized dashboard summary)
  TTL: 5 minutes (300 seconds)
  SIZE: ~2-5 KB per user

CACHE WRITE (on dashboard-summary request, cache miss):
  1. Backend aggregates data from MongoDB (6+ collections)
  2. Backend computes profile_completeness + recommended_step
  3. Backend serializes to JSON, stores in Redis with 5-min TTL
  4. Returns response to frontend

CACHE INVALIDATION (MANDATORY after these events):
  After any of these backend actions, execute:
    redis.delete(f"dashboard:{user_id}")

  INVALIDATION TRIGGERS:
  +-------------------------------+------------------------------------------+
  | EVENT                         | WHY INVALIDATE                           |
  +-------------------------------+------------------------------------------+
  | Resume parsed (5 credits)     | stats.resumes_parsed changes             |
  | Resume enhanced (10 credits)  | stats.resumes_enhanced changes           |
  | ATS scan (5 credits)          | stats.ats_scans + best_scores.ats_score  |
  | Job match (8 credits)         | stats.job_matches + best_scores.match    |
  | Assessment (15 credits)       | stats.assessments + interview_score      |
  | JD parsed (3 credits)         | usage log changes                        |
  | AI review (5 credits)         | usage log changes                        |
  | Profile updated               | profile_completeness changes             |
  | Resume created                | stats.resumes_created changes            |
  | Plan upgraded                 | credits + plan_name change               |
  | Onboarding completed          | onboarding_completed flag changes        |
  +-------------------------------+------------------------------------------+

  IMPLEMENTATION: In QuotaEnforcement middleware (after successful AI call):
    async def _invalidate_dashboard_cache(self, user_id: str):
        await self.redis.delete(f"dashboard:{user_id}")

  ALSO: Profile update endpoint should call this function.

FRONTEND CACHE BEHAVIOR:
  - Dashboard page does NOT cache locally (always fetches from backend)
  - Credit balance updated in real-time via X-Quota-Remaining headers
  - If dashboard-summary returns stale data (before Redis invalidation
    propagates), the X-Quota-Remaining header has the REAL-TIME balance

  CREDIT BALANCE SOURCE-OF-TRUTH RULE:
  The UI credit balance ALWAYS comes from X-Quota-Remaining header,
  NEVER from the cached dashboard-summary JSON body.

  Why: dashboard-summary is cached for 5 minutes. If user spends credits
  between cache refreshes, the JSON body has stale credits. The header
  is computed per-request by QuotaEnforcement middleware from Redis
  (real-time, never cached).

  Implementation:
    - CreditBadge reads from CreditContext.balance
    - CreditContext.balance is set ONLY by X-Quota-Remaining header
    - dashboard-summary JSON may include credits.remaining for reference
      but frontend IGNORES it for display -- header always wins
    - On responses without X-Quota-Remaining (non-quota endpoints):
      CreditContext retains last known value (no update)

THUNDERING HERD PREVENTION:
  - 5-min TTL is short enough that stale data is acceptable briefly
  - Only 1 user hits their own dashboard (no shared cache)
  - MongoDB aggregation is fast (~50-100ms for a single user)
  - No need for lock/mutex on dashboard cache

 9. CREDITS & QUOTA SYSTEM (Reconciled Units + Adaptive Modal)
================================================================================

CREDIT-TO-TOKEN RECONCILIATION:
  The backend has TWO unit systems that must be aligned:
    - "Tokens" (from token_service): actual LLM token consumption
    - "Credits" (from dashboard design): user-facing abstraction

  DECISION: Credits are the USER-FACING unit. Tokens are INTERNAL.
  Users never see "tokens." They only see "credits."

  MAPPING TABLE (See Appendix A for full table):
  +----------------------------+----------+-----------+---------------------+
  | FEATURE                    | CREDITS  | ~TOKENS   | NOTES               |
  +----------------------------+----------+-----------+---------------------+
  | Create Resume (Builder)    | FREE     | 0         | No AI call          |
  | Export Resume (PDF/DOCX)   | FREE     | 0         | No AI call          |
  | Parse Resume (Upload)      | 5 cr     | ~450 tok  | 1 LLM call          |
  | ATS Scan                   | 5 cr     | ~350 tok  | 1 LLM call          |
  | Enhance Resume             | 10 cr    | ~1200 tok | Multiple LLM calls  |
  | Job Match (Resume vs JD)   | 8 cr     | ~1200 tok | 3 LLM + 6 rule      |
  | Parse JD                   | 3 cr     | ~300 tok  | 1 LLM call          |
  | AI Resume Review           | 5 cr     | ~500 tok  | 1 LLM call          |
  | English Assessment         | 15 cr    | ~2000 tok | Multiple LLM calls  |
  | Browse Jobs                | FREE     | 0         | No AI call          |
  | Track Applications         | FREE     | 0         | No AI call          |
  | Update Profile             | FREE     | 0         | No AI call          |
  | View Past Results          | FREE     | 0         | No AI call          |
  +----------------------------+----------+-----------+---------------------+

  TOKEN SERVICE ALIGNMENT:
  Backend token_service has different costs (Resume Scan=50tok, etc.).
  These are INTERNAL metrics for cost tracking.
  The CREDIT system is a SEPARATE abstraction layer:
    - 1 credit != 1 token
    - Credits are a business unit; tokens are a cost unit
    - Backend deducts CREDITS (via Lua script), logs TOKENS (from AI response)
    - Admin sees both: credits consumed + actual tokens used + cost in INR

  SINGLE-SOURCE-OF-TRUTH RULE:
  +---------------------+-------------------------------+-------------------+
  | Context             | Unit Used                     | Source             |
  +---------------------+-------------------------------+-------------------+
  | User-facing UI      | CREDITS only                  | quota Redis keys   |
  | Quota enforcement   | CREDITS only                  | Lua script (Redis) |
  | Usage logging       | BOTH (credits + tokens)       | usage_logs (Mongo) |
  | Admin analytics     | BOTH (credits + tokens + INR) | token_analytics    |
  | AI Layer responses  | TOKENS only (tokens_used)     | LLM client         |
  | Cost calculations   | TOKENS -> INR conversion      | cost_tracker       |
  +---------------------+-------------------------------+-------------------+

  RULE: When displaying data to users, ALWAYS use "credits."
  When displaying data to admins, show credits AND tokens AND cost.
  The credit_cost_map (Appendix A) is the SINGLE CONFIG that defines
  the mapping. All frontend, backend, and admin code reads from this
  single config -- never hardcode credit costs in multiple places.

CROSS-TAB CREDIT SYNC:

  IMPLEMENTATION (in DashboardContext.tsx):
    const channel = new BroadcastChannel('careerbot-credits');

    // After any credit change (from X-Quota-Remaining header):
    channel.postMessage({ type: 'CREDIT_UPDATE', remaining: newBalance });

    channel.onmessage = (event) => {

17. AI LAYER EXPECTATIONS (What Exists + Backend Logging)
================================================================================

AI LAYER REQUIRES ZERO CODE CHANGES FOR THE DASHBOARD.

All 7 AI endpoints already return:
  - tokens_used: { total, prompt, completion }
  - cost_inr / cost_usd
  - from_cache: true/false
  - user_id, correlation_id

BACKEND LOGGING STRATEGY:
  AI Layer cost_records are IN-MEMORY ONLY (cleared per request lifecycle).
  There is NO persistent callback or webhook from AI Layer to Backend.

  SOLUTION: Backend captures token data from AI Layer HTTP responses.

  In every AI-calling backend endpoint:
    1. Call AI Layer (e.g., POST /api/v1/scoring/ats)
    2. Parse response body
    3. Extract: tokens_used, cost_inr, from_cache
    4. Insert into usage_logs collection (MongoDB)
    5. This is the durable usage record

  PSEUDO-CODE (in each AI-calling endpoint or shared utility):
    async def log_ai_usage(user_id, feature, credits, ai_response):
        tokens = ai_response.get("tokens_used", {}).get("total", 0)
        cost = ai_response.get("cost_inr", 0.0)
        cached = ai_response.get("from_cache", False)
        await usage_log_service.create({
            "user_id": user_id,
            "feature": feature,
            "credits_used": credits,
            "tokens_used": tokens,
            "cost_inr": cost,
            "from_cache": cached,
            "timestamp": datetime.utcnow()
        })

  REFUND ON AI FAILURE:
    If AI Layer returns 5xx or times out:
    1. Backend does NOT log usage (no entry in usage_logs)
    2. Backend refunds credits: INCRBY quota:{user_id}:balance {cost}
    3. Backend decrements feature count: DECR quota:{user_id}:feature:{name}
    4. Returns error to frontend with message "Credits not deducted"
    Reference: Blueprint V1.1 Section 9 (lines 963-970)
